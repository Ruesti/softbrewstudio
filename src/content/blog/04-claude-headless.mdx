Jetzt wird es interessant. NUC und Tailscale stehen, aber bisher ist das nur Infrastruktur ohne Inhalt. In diesem Teil geht es darum, wie ich Claude Code – das KI-Werkzeug, das für mich Programmieraufgaben erledigt – tatsächlich als Hintergrundprozess auf dem NUC laufen lasse. Ohne dass ich ein Fenster offen halten muss, und mit einer Überwachung, die genau weiß, wie viele Textbausteine ("Tokens") gerade verbraucht werden.

## Ein Agent wird gestartet

Man nennt das Starten eines solchen Hintergrundprozesses auch "spawnen" (von englisch "to spawn" – hervorbringen, erzeugen). Der Kern dafür ist ein kleines Python-Programm in meinem Daemon, das ich `spawn.py` genannt habe. Es stellt die Befehlszeile für den Aufruf von Claude Code zusammen und startet ihn im Hintergrund. So sieht die Grundform dieses Aufrufs aus:

```bash title="Grundform des Spawn-Aufrufs"
claude --bg --name <run_id> --permission-mode <mode> <prompt>
```

`--bg` sorgt dafür, dass Claude Code sich selbst in den Hintergrund schickt, statt das Fenster zu blockieren ("bg" wie "background"). `--name` gibt dem Lauf eine eindeutige Kennung, unter der ich ihn später wiederfinde. Und `--permission-mode` legt fest, wie viel der Agent ohne Rückfrage tun darf – dieser Wert kommt bei mir standardmäßig aus einer Konfigurationsdatei (`watcher.permission_mode: auto`, in derselben `pricing.yaml`, die ich schon in Teil 1 erwähnt habe).

Ein echtes Beispiel aus der Praxis, so wie ich es tatsächlich losgeschickt habe:

```bash title="Ein realer Spawn-Aufruf"
claude --bg --name verbrauch --permission-mode acceptEdits "…"
```

`acceptEdits` heißt: Der Agent darf Dateien bearbeiten, ohne bei jeder einzelnen Änderung nachzufragen – praktisch für längere, unbeaufsichtigte Läufe, aber eben auch ein Grund, warum die Budget-Überwachung aus diesem Artikel so wichtig ist.

## Die Auftrags-Kennung aus der Ausgabe herausfischen

Wenn Claude Code im Hintergrund startet, gibt es eine Textzeile aus, die unter anderem eine achtstellige Kennung enthält. Mein Daemon liest diese Kennung mit einer einfachen Regel heraus: acht bestimmte Zeichen nach dem Wort "backgrounded" im Ausgabetext, gefunden über ein sogenanntes Muster-Suchverfahren (`([0-9a-f]{8})`). Diese Kennung ist ab dann der Schlüssel, mit dem ich den Lauf im gesamten System wiederfinde – im Daemon, im Cockpit (Teil 5), überall.

## Den Lauf über einfache Befehle steuern

Ist der Auftrag einmal gestartet, steuere ich seinen weiteren Lebensweg komplett über die eingebauten Befehle von Claude Code selbst:

```bash title="Laufende Jobs auflisten"
claude agents --json --all
```

```bash title="Einen Job stoppen"
claude stop <job_id>
```

```bash title="Einen abgeschlossenen Job aufräumen"
claude rm <job_id>
```

```bash title="An einen laufenden Job andocken"
claude attach <job_id>
```

Das ist bewusst schmal gehalten: kein eigenes, zusätzliches Regelwerk – ich nutze das, was Claude Code selbst schon mitbringt, und baue meinen Daemon nur als dünne Schicht darüber.

## Wo der Zustand wirklich liegt

Jeder Job legt in einer eigenen Datei (`~/.claude/jobs/<id>/state.json`) einen Zustand ab. Aber – und das ist der Teil, der mich am meisten überrascht hat, als ich anfing, den Verbrauch live zu verfolgen – die aktuellen Zahlen zum Textbaustein-Verbrauch stehen dort nicht drin. Diese Datei sagt mir nur, ob ein Job läuft, beendet ist oder fehlgeschlagen ist, aber nichts über den laufenden Verbrauch.

Die eigentlichen Nutzungsdaten holt sich mein Daemon aus einer ganz anderen Quelle: dem vollständigen Gesprächsprotokoll der Sitzung, das in einer Datei unter `~/.claude/projects/<slug>/<sessionId>.jsonl` liegt. Eine Funktion namens `_process_transcript` liest diese Datei fortlaufend – Zeile für Zeile, immer nur die neuen Einträge seit dem letzten Durchlauf – und liest daraus die Zahlen für eingehende, ausgehende und zwischengespeicherte Textbausteine heraus.

## Die Lektion mit den zwischengespeicherten Textbausteinen

Und hier kommt die Geschichte, die mich am meisten gelehrt hat. In der ersten Version meiner Budget-Berechnung habe ich schlicht alle vier Kategorien von Textbausteinen aus dem Protokoll zusammengezählt: eingehend, ausgehend, neu zwischengespeichert und aus dem Zwischenspeicher gelesen. Klang nach der naheliegendsten, korrektesten Lösung.

Das Problem: Die Kategorie "aus dem Zwischenspeicher gelesen" zählt bei jeder einzelnen Gesprächsrunde den kompletten bisherigen Gesprächsverlauf neu mit – und der kann bei einem längeren Agentenlauf schnell über 100.000 Textbausteine groß sein. Jede Runde, egal wie klein die eigentliche Antwort war, hat also den gesamten bisher aufgelaufenen Verlauf noch einmal ins Budget eingerechnet. Das Ergebnis: Ein Budget, das eigentlich bei 40.000 Textbausteinen gedeckelt war, lief in der Praxis auf 199.799 Textbausteine hoch, bevor irgendetwas gestoppt hat.

<Callout type="warn">
Lehrstück aus der Praxis: Meine erste Budget-Messung zählte einfach alle vier Kategorien zusammen. Weil die Kategorie "aus dem Zwischenspeicher gelesen" bei jeder Runde den kompletten Gesprächsverlauf (oft 100.000+ Textbausteine) erneut mitzählt, lief ein eigentlich auf 40.000 Textbausteine gedeckeltes Budget auf 199.799 Textbausteine hoch, bevor der Stopp griff. Der Fix: Die Budget-Berechnung (`_budget_tokens`) lässt diese Kategorie jetzt außen vor. Die Kostenberechnung dagegen behält sie bewusst bei – denn auch wiederverwendeter Gesprächsverlauf kostet echtes Geld, auch wenn er fürs Budget nicht zählen soll.
</Callout>

Der Unterschied zwischen Budget und Kosten ist also feiner, als er zunächst aussieht: Fürs Budget – die Frage "darf dieser Agent noch weiterlaufen?" – zählt nur, was tatsächlich neu verarbeitet wurde. Für die Kostenrechnung – "was hat dieser Lauf gekostet?" – zählt dagegen alles, einschließlich wiederverwendetem Gesprächsverlauf, weil auch der abgerechnet wird.

Seit diesem Fix funktioniert das erwartete Verhalten zuverlässig: Überschreitet ein Lauf sein Budget, meldet mein Überwachungsprogramm das als `budget_exceeded`, und der Stopp-Befehl beendet den Job tatsächlich. Kein stiller Fehlschlag, kein Job, der einfach munter weiterläuft, während im Hintergrund die Kosten steigen.

## Ausblick

Damit läuft Claude Code jetzt zuverlässig unsichtbar im Hintergrund auf dem NUC, mit einer Budget-Kontrolle, die auf die harte Tour gelernt hat, korrekt zu zählen. Aber ein einzelner Job im Hintergrund ist erst der Anfang. In Teil 5 zeige ich, wie aus einzelnen Läufen ein ganzes System aus Ereignissen, Zuständen und einem Cockpit wird – inklusive Steuerungsbefehlen, die im Code längst existieren, aber in einer veralteten Anleitung noch fehlen.
