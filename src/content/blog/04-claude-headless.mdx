Jetzt wird es interessant. NUC und Tailscale stehen, aber bisher ist das nur Infrastruktur ohne Inhalt. In diesem Teil geht es darum, wie ich Claude Code tatsächlich als Hintergrundprozess auf dem NUC laufen lasse – ohne dass ich ein Terminal offen halten muss, und mit einer Überwachung, die genau weiß, wie viele Tokens gerade verbraucht werden.

## Ein Agent wird gespawnt

Der Kern ist ein Python-Modul in meinem Daemon, das ich `spawn.py` genannt habe. Es baut die argv-Liste für den Claude-Code-Aufruf zusammen und startet ihn im Hintergrund:

```bash title="Grundform des Spawn-Aufrufs"
claude --bg --name <run_id> --permission-mode <mode> <prompt>
```

`--bg` sorgt dafür, dass Claude Code sich selbst in den Hintergrund schickt, statt das Terminal zu blockieren. `--name` gibt dem Lauf eine eindeutige ID, unter der ich ihn später wiederfinde. Und `--permission-mode` legt fest, wie viel der Agent ohne Rückfrage tun darf – dieser Wert kommt bei mir standardmäßig aus der Konfiguration (`watcher.permission_mode: auto` in derselben `pricing.yaml`, die ich schon in Teil 1 erwähnt habe).

Ein echtes Beispiel aus der Praxis, so wie ich es tatsächlich abgeschickt habe:

```bash title="Ein realer Spawn-Aufruf"
claude --bg --name verbrauch --permission-mode acceptEdits "…"
```

`acceptEdits` heißt: Der Agent darf Dateien bearbeiten, ohne bei jeder einzelnen Änderung nachzufragen – praktisch für längere, unbeaufsichtigte Läufe, aber eben auch ein Grund, warum das Budget-Tracking aus diesem Artikel so wichtig ist.

## Die Job-ID aus der Ausgabe fischen

Wenn Claude Code im Hintergrund startet, gibt es auf stdout eine Zeile aus, die unter anderem eine achtstellige Hex-ID enthält. Mein Daemon parst diese ID mit einer simplen Regel: acht Hex-Zeichen nach dem Wort "backgrounded" im Ausgabetext, per regulärem Ausdruck `([0-9a-f]{8})`. Diese ID ist ab dann der Schlüssel, mit dem ich den Lauf im gesamten System wiederfinde – im Daemon, im Cockpit (Teil 5), überall.

## Lebenszyklus über die CLI

Ist der Job einmal gestartet, steuere ich seinen weiteren Lebenszyklus komplett über die Claude-Code-CLI selbst:

```bash title="Laufende Jobs auflisten"
claude agents --json --all
```

```bash title="Einen Job stoppen"
claude stop <job_id>
```

```bash title="Einen abgeschlossenen Job aufräumen"
claude rm <job_id>
```

```bash title="An einen laufenden Job andocken"
claude attach <job_id>
```

Das ist bewusst schmal gehalten: kein eigenes Protokoll, keine Extra-Abstraktion – ich nutze das, was die CLI selbst mitbringt, und baue meinen Daemon als dünne Schicht darüber.

## Wo der Zustand wirklich liegt

Jeder Job legt unter `~/.claude/jobs/<id>/state.json` eine Zustandsdatei an. Aber – und das ist der Teil, der mich am meisten überrascht hat, als ich anfing, den Verbrauch live zu verfolgen – die aktuellen Token-Zahlen stehen dort nicht drin. Die `state.json` sagt mir, ob ein Job läuft, beendet ist oder fehlgeschlagen ist, aber nichts über den laufenden Verbrauch.

Die eigentlichen Nutzungsdaten holt sich mein Daemon aus einer ganz anderen Quelle: dem Transcript der Session, das unter `~/.claude/projects/<slug>/<sessionId>.jsonl` liegt. Eine Funktion namens `_process_transcript` liest diese Datei inkrementell – Zeile für Zeile, immer nur die neuen Einträge seit dem letzten Durchlauf – und extrahiert daraus die Token-Zahlen für Input, Output und Cache.

## Die Lektion mit den Cache-Tokens

Und hier kommt die Geschichte, die mich am meisten gelehrt hat. In der ersten Version meiner Budget-Berechnung habe ich schlicht alle vier Token-Kategorien aus dem Transcript aufsummiert: Input, Output, Cache-Write und Cache-Read. Klang nach der naheliegendsten, korrektesten Lösung.

Das Problem: `cache_read` zählt bei jeder einzelnen Gesprächsrunde den kompletten bisherigen Kontext neu mit – und der kann bei einem längeren Agentenlauf schnell über 100.000 Tokens groß sein. Jede Runde, egal wie klein die eigentliche Antwort war, hat also den gesamten aufgelaufenen Kontext noch einmal ins Budget eingerechnet. Das Ergebnis: Ein Budget, das eigentlich bei 40.000 Tokens gedeckelt war, lief in der Praxis auf 199.799 Tokens hoch, bevor irgendetwas gestoppt hat.

<Callout type="warn">
Lehrstück aus der Praxis: Meine erste Budget-Metrik summierte `input + output + cache_write + cache_read`. Weil `cache_read` bei jeder Runde den kompletten Kontext (oft 100.000+ Tokens) erneut mitzählt, lief ein eigentlich auf 40.000 Tokens gedeckeltes Budget auf 199.799 Tokens hoch, bevor der Stopp griff. Der Fix in Iteration 2: Die Budget-Berechnung (`_budget_tokens`) lässt `cache_read` jetzt außen vor. Die Kostenberechnung dagegen behält `cache_read` bewusst bei – denn auch wiederverwendeter Cache-Kontext kostet echtes Geld, auch wenn er fürs Budget nicht zählen soll.
</Callout>

Der Unterschied zwischen Budget und Kosten ist also feiner, als er zunächst aussieht: Fürs Budget – die Frage "darf dieser Agent noch weiterlaufen?" – zählt nur, was tatsächlich neu verarbeitet wurde. Für die Kostenrechnung – "was hat dieser Lauf gekostet?" – zählt dagegen alles, inklusive wiederverwendetem Cache, weil auch der abgerechnet wird.

Seit diesem Fix funktioniert das erwartete Verhalten zuverlässig: Überschreitet ein Lauf sein Budget, meldet mein Watcher-Modul das als `budget_exceeded`, und `claude stop` beendet den Job tatsächlich. Kein stiller Fehlschlag, kein Job, der einfach munter weiterläuft, während im Hintergrund die Kosten steigen.

## Ausblick

Damit läuft Claude Code jetzt zuverlässig headless auf dem NUC, mit einer Budget-Kontrolle, die auf die harte Tour gelernt hat, korrekt zu zählen. Aber ein einzelner Job im Hintergrund ist erst der Anfang. In Teil 5 zeige ich, wie aus einzelnen Läufen ein ganzes System aus Events, Zuständen und einem Cockpit wird – inklusive Action-Routen, die im Code längst existieren, aber in einer veralteten Doku fehlen.
